## ۱. سیستم فیلتر مبتنی بر URL (سئو)

### مسئله
فیلترهای صفحه دسته‌بندی فقط در state نگهداری می‌شدند؛ URL تغییر نمی‌کرد. یعنی هیچ فیلتری قابل اشتراک‌گذاری، بوکمارک یا ایندکس نبود.

### راه‌حل
فرمت URL بر پایه **slug خوانا**، نه شناسه:

```
/categories/printer?print-type=laser&usage-type=single-function&brand=hp
```

**چرا slug انگلیسی و نه فارسی؟**
کلمه کلیدی در URL یکی از ضعیف‌ترین سیگنال‌های رنکینگ است، در حالی که slug فارسی هزینه‌های واقعی دارد: URL می‌شود `%D9%84%DB%8C...`، گزارش‌های Search Console خوانا نیست، و مشکل نرمال‌سازی ی/ک عربی برمی‌گردد.

### فایل‌های کلیدی

| فایل | نقش |
|---|---|
| `lib/slug.ts` | `slugify`، `isValidSlug`، ترنسلیت فارسی→لاتین، لیست کلمات رزروشده |
| `lib/catalog.ts` | **منبع واحد** منطق فیلتر — مشترک بین SSR و API |
| `lib/category-data.ts` | داده دسته‌بندی مستقیم از Prisma (بدون HTTP به خود) |
| `scripts/backfill-attr-slugs.ts` | پرکردن slugهای خالی/نامعتبر با دیکشنری + ترنسلیت |

### باگ‌های رفع‌شده در مسیر

**منطق AND در فیلتر ویژگی‌ها.** کد قبلی همه مقادیر را در یک `some` می‌گذاشت:
```ts
where.AND.push({ attributes: { some: { attributeValueId: { in: allValues } } } });
```
یعنی «لیزری **یا** تک‌کاره». درست: به ازای هر ویژگی یک `some` جدا، ترکیب با `AND`. داخل یک ویژگی OR، بین ویژگی‌ها AND.

**`pageSize=1`.** تابع `toInt` وقتی پارامتر نبود `Number(null) === 0` را معتبر می‌شمرد و fallback را نادیده می‌گرفت. **هر فراخوانی `/api/products` بدون `pageSize` فقط یک محصول برمی‌گرداند.**

**فیلتر چندبرندی.** `if (selectedBrands.length === 1)` باعث می‌شد انتخاب دو برند بی‌صدا نادیده گرفته شود.

**حلقه بی‌نهایت سینک URL.** `router.replace` → رندر مجدد سرور کامپوننت → آبجکت `category` جدید → `useMemo` بازساخته → `buildParams` identity جدید → افکت دوباره فایر. رفع با مقایسه‌ی آدرس فعلی مرورگر پیش از نوشتن.

**fail-closed.** فیلتر ناموجود (`?print-type=nonexistent`) قبلاً بی‌صدا نادیده گرفته می‌شد و همه محصولات برمی‌گشتند — یعنی بی‌نهایت URL با محتوای یکسان. حالا نتیجه خالی برمی‌گردد.

## ۲. سیاست ایندکس (Faceted Navigation)

بدون کنترل، هر ترکیب فیلتر یک URL ایندکس‌شدنی می‌سازد → index bloat و صفحات نازک تکراری.

| نوع URL | robots | canonical |
|---|---|---|
| دسته بدون فیلتر | `index, follow` | خودش |
| فیلتر معمولی کاربر | `noindex, follow` | دسته پایه |
| `sort` / `page>1` / بازه قیمت | `noindex, follow` | دسته پایه |
| صفحه فرود تعریف‌شده در ادمین | `index, follow` | خودش |

`follow` عمدی است: صفحه ایندکس نشود ولی گوگل لینک محصولات داخلش را دنبال کند.

`buildBaseMetadata` در `lib/seo.ts` دو پارامتر جدید گرفت: `followWhenNoIndex` و `canonicalPath`.

## ۳. صفحات فرود سئو

### تصمیم معماری: مسیر اختصاصی، نه query string

```
/collections/printer-laser-single-function
```

هر ترکیب فیلتری که با یک صفحه فرود منطبق باشد، با **۳۰۷ به مسیر canonical ریدایرکت می‌شود**. یک محتوا، یک آدرس.

### مدل

```prisma
model LandingPage {
  slug        String   @unique
  categoryId  String
  filters     Json      // { "print-type": "laser", "usage-type": "single-function" }
  title       String
  h1          String
  description String
  intro       String?
  bodyHtml    String?
  isActive    Boolean  @default(true)
  isIndexable Boolean  @default(true)
}
```

`filters` به‌صورت `Json` چون شکلش متغیر است و همیشه یکجا خوانده می‌شود. هزینه‌اش: اگر slug یک ویژگی عوض شود، صفحه بی‌صدا می‌شکند — که با محافظت زیر پوشش داده شد.

### محافظت از شکستن

`PUT /api/admin/attributes` قبل از تغییر slug بررسی می‌کند آیا در صفحه فرودی استفاده شده. اگر بله، `409` با `needsForce: true` برمی‌گرداند و UI تأیید می‌گیرد.

### sitemap

فقط صفحات فرودی که `isActive && isIndexable` **و حداقل یک محصول دارند** وارد می‌شوند. صفحه فرود بدون محصول = صفحه نازک = ضرر خالص.

### لینک داخلی

چیپ‌های اسلایدی بالای لیست محصولات، **خودکار از جدول `LandingPage`**. هر سایت دیتابیس خودش را دارد، پس نیازی به لینک‌سازی دستی نیست. یک ردیف با اسکرول افقی (نه `flex-wrap`) که در موبایل چیدمان را به هم نریزد.

## ۴. سیستم استقرار

### چرا push و نه pull

گزینه‌ی «هر سایت خودش بروز شود» بررسی و **رد شد**: مکانیزمی که کد را از اینترنت می‌گیرد و روی سرور مشتری اجرا می‌کند، یک کانال RCE توزیع‌شده است. اگر سرور توزیع هک شود، همه سایت‌های مشتریان هک می‌شوند.

با push:
- احراز هویت و رمزنگاری از قبل توسط SSH حل شده
- بدون نیاز به دسترسی npm روی سرور (`node_modules` منتقل می‌شود)
- اگر چیزی بشکند، توسعه‌دهنده همان لحظه پشت ترمینال است

> کلیدهای Ed25519 در `scripts/release/keygen.mjs` ساخته شدند و برای روزی که self-service لازم شود نگه داشته می‌شوند. `release-keys/` در `.gitignore` است.

### `scripts/deploy/deploy.mjs`

```bash
node scripts/deploy/deploy.mjs 9dm --dry-run
node scripts/deploy/deploy.mjs mahamprint
node scripts/deploy/deploy.mjs --tier production
```

مراحل:
1. بررسی اتصال، وجود `.env` و پروسه pm2
2. **بکاپ دیتابیس** + تأیید حجم واقعی
3. **دروازه ایمنی** — اگر محصول > ۱۰۰ و بکاپ < ۵۰KB، متوقف
4. تأیید دستی `backup-ok` برای هر سایت پروداکشن
5. بکاپ کد فعلی
6. rsync سورس (بدون `node_modules`، `public/*`، `.env`، `ecosystem.config.js`)
7. `node_modules` با `tar` روی ssh — **فقط اگر `pnpm-lock.yaml` تغییر کرده**
8. `prisma generate` → `backfill-attr-slugs` → `migrate deploy` → `next build`
9. تأیید `BUILD_ID` (build ناقص → ری‌استارت انجام نمی‌شود)
10. `pm2 restart` + health check روی `127.0.0.1:PORT`
11. بازگردانی خودکار کد در صورت شکست

### درس‌های آموخته

- **`--delete` در rsync با `node_modules` نسازید.** symlinkهای تودرتوی pnpm باعث اسکن بی‌نهایت مقصد می‌شوند. `tar` این مشکل را ندارد.
- **`ecosystem.config.js` نباید منتقل شود** — نام و پورت pm2 هر سایت متفاوت است.
- **health check باید از داخل سرور باشد** (`127.0.0.1:PORT`)، نه از لپ‌تاپ. تست از بیرون به‌خاطر شبکه `000` می‌دهد و rollback بی‌دلیل اجرا می‌شود.
- **بکاپ باید حجمش تأیید شود.** یک `pg_dump` شکست‌خورده که به `gzip` پایپ شده، فایل ۲۰ بایتی می‌سازد و `&&` را رد می‌کند.
- **پسورد با `@` یا `%` در `DATABASE_URL`** باعث می‌شود `pg_dump` بخشی از پسورد را hostname بخواند. راه‌حل: متغیرهای `PGHOST`/`PGUSER`/`PGPASSWORD` جدا، نه URL کامل.
- **`backfill-attr-slugs` باید قبل از `migrate deploy` اجرا شود** — وگرنه migration یکتاسازی روی slugهای خالی می‌شکند.
- **`set -o pipefail` در `dash` نیست.** از `bash -s` استفاده کنید.

## ۵. باگ‌های متفرقه رفع‌شده

**جستجوی موبایل.** `SearchPageClient` به `/api/search` درخواست می‌داد که وجود ندارد (روت واقعی `/api/store/search` است) → ۴۰۴ → catch → «نتیجه‌ای یافت نشد». دسکتاپ کار می‌کرد چون از SSR می‌آمد. جستجوی زنده با debounce و `AbortController` هم اضافه شد.

**Redis.** `REDIS_URL ?? "redis://localhost:63791"` باعث می‌شد بدون پیکربندی هم اتصال بی‌نهایت retry شود. لاگ چهار سایت پر می‌شد و `Collecting page data` در build کند می‌شد (۹۸ ثانیه روی مای‌مونتا). حالا: `lazyConnect`، `retryStrategy` با سقف، لاگ فقط یک بار، و `redis: IORedis | null`.

**`alt` بنرها.** `function Banner({ alt = "بنر" })` — مقدار پیش‌فرض فقط برای `undefined` اعمال می‌شود. والد `null` از دیتابیس می‌داد، پس React صفت را حذف می‌کرد. رفع با `alt={alt || "بنر"}` در خود JSX.

**`slugify` پنل ادمین.** الگوی `[^\w\-]` در جاوااسکریپت فقط `[A-Za-z0-9_]` را نگه می‌دارد، پس عنوان فارسی کاملاً پاک می‌شد و slug `-` یا رشته خالی تولید می‌کرد. جایگزین شد با `lib/slug.ts` + ولیدیشن + امکان ویرایش ویژگی از پنل.

**`SITE_URL` تنظیم‌نشده در لوکال** → همه canonicalها `example.com`. سرورها درست بودند.

**`catch` خاموش sitemap.** خطا باعث می‌شد فقط ۵ صفحه استاتیک برگردد و گوگل فکر کند سایت خالی شده. حالا `throw` می‌کند تا ۵۰۰ بدهد (خطای موقت، نه واقعیت). `take` از ۵۰۰۰ به ۴۵۰۰۰ رسید.

**دسترسی‌پذیری.** `aria-label` برای لینک‌های آیکونی (`/search`، `/cart`، `/user`)، دکمه بستن منو، و لینک‌های تکراری «مشاهده همه محصولات».

## ۷. نکات فنی برای آینده

**Prisma 7** دیگر `new PrismaClient()` بدون آپشن را نمی‌پذیرد. اسکریپت‌ها باید `import { prisma } from "../lib/prisma"` کنند و با `npx tsx --env-file=.env` اجرا شوند.

**`proxy.ts`** همان middleware پروژه است (Next.js 16 نامش را عوض کرده). کل `/admin/*` و `/api/admin/*` را با JWT محافظت می‌کند — پس روت‌های ادمین جدید خودکار پوشش داده می‌شوند.

**`ProductAttribute` دارای `@@unique([productId, attributeId])`** است — هر محصول به ازای هر ویژگی دقیقاً یک مقدار دارد. این منطق فیلتر (OR داخل ویژگی، AND بین ویژگی‌ها) را قطعی می‌کند.

**`AttributeValue.slug`** حالا `@@unique([attributeId, slug])` دارد. یکتایی در سطح ویژگی کافی است چون کلید URL خود slug ویژگی است — `?color=red` و `?frame-color=red` تداخلی ندارند.

**صفحه دسته‌بندی حالا dynamic است** (به‌خاطر `searchParams`). هر بازدید یک کوئری دیتابیس می‌زند. اگر ترافیک بالا رفت، `unstable_cache` روی `getCategoryData` بگذارید — آن داده کم تغییر می‌کند.

**nginx مهام‌پرینت و مای‌مونتا `location /_next/static/` دارند** و مستقیم از `.next/static` سرو می‌کنند. بین اتمام build و ری‌استارت pm2، چند ثانیه احتمال خطای chunk برای کاربران آنلاین وجود دارد. deploy در ساعت کم‌ترافیک بهتر است.
