# سیستم ریدایرکت و گزارش ۴۰۴

مدیریت ریدایرکت‌ها از پنل ادمین، مثل افزونه‌های سئوی وردپرس — بدون نیاز به SSH یا دیپلوی.

---

## چه چیزی اضافه شد

| فایل | نقش |
|------|-----|
| `prisma/schema.prisma` | مدل‌های `Redirect` و `NotFoundLog` + enum `RedirectMatch` |
| `lib/redirects.ts` | نرمال‌سازی مسیر، اعتبارسنجی، منطق تطبیق — **بدون وابستگی به Prisma** |
| `lib/redirectCache.ts` | کش درون‌حافظه‌ای قواعد برای proxy |

| `app/api/internal/redirects/route.ts` | تأمین قواعد برای proxy + شمارش بازدید |
| `app/api/internal/not-found/route.ts` | ثبت ۴۰۴ |
| `app/api/admin/redirects/route.ts` | CRUD + ورود دسته‌ای CSV |

| `app/admin/layout.tsx` | گروه منوی «سئو» |

## نحوه‌ی کار

```
درخواست
   ↓
proxy.ts  ──►  احراز هویت ادمین/فروشنده (بدون تغییر)
   ↓
handleRedirects()
   ↓
getRules()  ──►  کش حافظه (TTL ۶۰ ثانیه)
   ↓ (فقط اگر کش منقضی شده)
GET /api/internal/redirects  ──►  Prisma
   ↓
matchPath()  ──►  EXACT، بعد PREFIX، بعد REGEX
   ↓
301 / 302 / 307 / 308 / 410
```

### چرا کش

proxy روی **هر** درخواست صفحه اجرا می‌شود. بدون کش، هر بازدید یک کوئری اضافه به دیتابیس می‌زد — روی سرورهایی که TTFB‌شان از قبل بالاست این فاجعه است. با کش، جستجو یک `Map` در حافظه است و حداکثر یک کوئری در هر ۶۰ ثانیه انجام می‌شود.

### چرا از طریق fetch و نه Prisma مستقیم

proxy ممکن است روی edge runtime اجرا شود که Prisma در آن کار نمی‌کند. یک route handler معمولی (Node) قواعد را می‌خواند و proxy همان را می‌گیرد.

### چرا از localhost و نه origin درخواست می‌فرستیم

`internalBase()` در `lib/redirectCache.ts` همیشه `http://127.0.0.1:$PORT` را می‌سازد و عمداً از `origin` درخواست کاربر استفاده نمی‌کند.

**این باگ در تست روی سایت دمو پیدا شد.** نسخه‌ی اول از `origin` استفاده می‌کرد؛ نتیجه این بود که ریدایرکت روی `http://127.0.0.1:3003` درست کار می‌کرد ولی از `https://9dm.ir` نه — چون اپ برای خواندن قواعد خودش به **آدرس عمومی خودش** درخواست می‌داد و آن ترافیک باید از سرور بیرون می‌رفت، از DNS و CDN رد می‌شد و برمی‌گشت.

`PORT` را pm2/Next ست می‌کند؛ اگر نبود ۳۰۰۰ پیش‌فرض است. در صورت نیاز با `INTERNAL_BASE_URL` قابل بازنویسی است.

> درس این ماجرا: تست روی پورت مستقیم اپ کافی نیست. حتماً از آدرس عمومی هم تست کنید.

### چرا تابع invalidate نداریم

proxy و route handlerها نمونه‌ی ماژول جداگانه دارند (و با pm2 چندپروسه‌ای حتی حافظه‌ی جداگانه). یک `invalidate()` که از API صدا زده شود روی کش proxy اثری نمی‌گذاشت — تابعی می‌شد که ظاهراً کار می‌کند و در عمل نه. به‌جایش TTL کوتاه است و در پیام ادمین به کاربر گفته می‌شود که **تا ۶۰ ثانیه** طول می‌کشد.

## انواع تطبیق

| نوع | مبدأ | نمونه‌ی ورودی | نتیجه |
|-----|------|----------------|-------|
| `EXACT` | `/old-page` | `/old-page` | فقط همین مسیر |
| `PREFIX` | `/blog` | `/blog/my-article` | `/mag/my-article` — دنباله حفظ می‌شود |
| `REGEX` | `^/product/(\d+)/.*$` | `/product/147/x` | با `$1` در مقصد |

**ترتیب اولویت عمدی است:** EXACT ← PREFIX ← REGEX. بین PREFIXها طولانی‌ترین مبدأ برنده است تا `/blog/archive` بر `/blog` بچربد.

## کدهای وضعیت

| کد | کاربرد |
|----|--------|
| ۳۰۱ | جابه‌جایی دائمی — گزینه‌ی پیش‌فرض برای مهاجرت |
| ۳۰۲ | موقت |
| ۳۰۷ / ۳۰۸ | مثل ۳۰۲ / ۳۰۱ ولی متد HTTP حفظ می‌شود |
| ۴۱۰ | صفحه عمداً حذف شده — گوگل سریع‌تر از ایندکس برمی‌دارد. مقصد لازم ندارد |

## نرمال‌سازی مسیر

هر مبدأ پیش از ذخیره یکسان‌سازی می‌شود (`normalizePath` در `lib/redirects.ts`):

- دامنه حذف می‌شود — می‌توانید آدرس کامل paste کنید
- query string و hash حذف می‌شوند
- `/` ابتدایی اضافه، `/` انتهایی حذف
- **حروف کوچک می‌شود** — چون nginx هم روی کلیدهای map حساس به بزرگی نیست و دو قاعده‌ی متفاوت گیج‌کننده بود

مبدأ نوع `REGEX` نرمال **نمی‌شود** — الگو باید دست‌نخورده بماند.

آدرس‌های فارسی هم به شکل encode و هم decode تطبیق داده می‌شوند، چون مرورگرها و خزنده‌ها هر دو شکل را می‌فرستند.

## گزارش ۴۰۴

`components/seo/NotFoundReporter.tsx` در `app/not-found.tsx` قرار دارد و هر بازدید ۴۰۴ را ثبت می‌کند.

**چرا سمت کلاینت:** صفحه‌ی `not-found` سرور-کامپوننت است و ممکن است استاتیک رندر شود؛ در آن حالت کد سمت سرور فقط موقع build اجرا می‌شد.

محافظ‌ها:
- در `NODE_ENV !== production` اصلاً ثبت نمی‌شود
- هر مسیر در هر نشست فقط یک‌بار (`sessionStorage`)
- مسیرهای استاتیک و داخلی رد می‌شوند
- سقف ۵۰۰۰ ردیف — بعد از آن فقط شمارنده‌ی موارد موجود بالا می‌رود
- شکست ثبت آمار هرگز صفحه‌ی کاربر را نمی‌شکند

از صفحه‌ی گزارش، دکمه‌ی «ساخت ریدایرکت» قاعده را می‌سازد و ردیف ۴۰۴ را حذف می‌کند.

## ورود دسته‌ای CSV

در `/admin/seo/redirects` → «ورود دسته‌ای». هر خط:

```
مبدأ,مقصد,کد,نوع,یادداشت
/product/147/old-name,/products/new-name,301,EXACT,مهاجرت
/old-blog,/mag,301,PREFIX
```

کد و نوع اختیاری‌اند (پیش‌فرض ۳۰۱ و EXACT). خط عنوان و خطوط شروع‌شده با `#` نادیده گرفته می‌شوند.

دو حالت برای مبدأ تکراری: **رد شود** یا **بازنویسی شود**. عمداً در یک تراکنش نیست — در فایل چندهزارتایی یک ردیف خراب نباید کل ورود را برگرداند؛ هر ردیف جدا پردازش و در گزارش نهایی شمرده می‌شود.

## امنیت

- `/api/admin/*` از قبل در `proxy.ts` با نقش `ADMIN` محافظت می‌شود — تست شد، بدون توکن ۴۰۱ می‌دهد
- `/api/internal/*` با هدر `x-redirect-cache-token` محافظت می‌شود

**متغیر محیطی لازم:**

```bash
REDIRECT_CACHE_TOKEN=<رشته‌ی تصادفی، مثلاً openssl rand -hex 24>
```

اگر تنظیم نشود، مسیر داخلی باز می‌ماند (رفتار سازگار، سایت نمی‌شکند) ولی برای production باید ست شود. چون `.env` در rsync دیپلوی مستثناست، **روی هر سرور باید دستی اضافه شود**.

## رابطه با nginx

این سیستم جایگزین nginx **نیست**. تقسیم کار:

| مورد | کجا |
|------|-----|
| مهاجرت‌های حجیم (هزاران ریدایرکت یک‌باره) | nginx `map` — سریع‌تر، بدون فشار روی اپ |
| ریدایرکت‌های جاری و روزمره | پنل ادمین |

نمونه‌ی واقعی: ۲۵۲۰ ریدایرکت مهاجرت mahamprint.com در `/etc/nginx/mahamprint-redirects.map` است و دو ماه دیگر برداشته می‌شود. جزئیات در `docs/audits/mahamprint/DEPLOYED-CHANGES.md`.

## نکات نگهداری

- **`config.matcher` در `proxy.ts` تغییر کرد** — قبلاً فقط `/admin` و `/seller` را می‌گرفت، حالا همه‌ی صفحات را می‌بیند تا ریدایرکت‌ها کار کنند. فایل‌های استاتیک و `/api/internal` بیرون نگه داشته شده‌اند.
- `shouldSkip()` در `lib/redirects.ts` دومین لایه‌ی محافظ است. اگر مسیر جدیدی اضافه کردید که نباید ریدایرکت شود، آنجا اضافه کنید نه فقط در matcher.
- قاعده‌ی regex خراب کل تطبیق را نمی‌شکند — فقط خودش رد می‌شود.
- اگر مقصد با مبدأ یکی باشد، ریدایرکت انجام نمی‌شود (جلوگیری از حلقه). فرم هم موقع ذخیره هشدار می‌دهد.
- اسلش انتهایی را خود Next با ۳۰۸ نرمال می‌کند و بعد قاعده‌ی ما اجرا می‌شود — یعنی `/old-page/` دو هاپ می‌خورد ولی درست به مقصد می‌رسد.
